================================================================================
GYM TRACKER - PROJECT SUMMARY
Last updated: 2026-05-04
================================================================================

This project is a Hebrew RTL mobile-first fitness PWA built with:
- Next.js 15 App Router
- React 19
- TypeScript
- Supabase
- Vercel

The product tracks:
- workouts
- nutrition
- bodyweight
- body measurements
- weekly goal focus
- recovery/data completeness

The app uses deterministic business logic and fixed recommendation templates.
There is no LLM-generated recommendation text in the core product flow.

2. AUTHENTICATION AND IDENTITY
================================================================================

Provider:

Current auth characteristics:
- email/password flow is implemented
- app session state is exposed through `src/lib/session.tsx`

Identity model:

- `sync_profile_from_auth_user()` upserts profile rows from `auth.users`
- duplicate invalid email linkage raises `PROFILE_EMAIL_ALREADY_LINKED`

4. HOME PAGE
================================================================================

Route:
- `app/home/page.tsx`

Home loads in parallel:
- bodyweight logs
- nutrition logs
- workout sessions
- user profile
- active workout program

Main sections:
- weight status
- protein today
- calories today
- bodyweight entry
- bodyweight chart
- daily recommendation
- weekly goal box
- recovery/data-completeness messaging

Daily nutrition reset rule:
- "today" is determined only by `Asia/Jerusalem`
- source of truth: `src/lib/date/getIsraelDateKey.ts`
- all Home daily nutrition filters use the same Israel date key

Midnight rollover behavior:
- Home computes exact milliseconds until next midnight in Israel
- schedules one `setTimeout`
- when it fires, local today state is updated
- derived daily nutrition values recalculate automatically
- next midnight timeout is scheduled again

Result:
- if the user stays on Home across midnight in Israel, protein/calories switch
  to the new day automatically
- if no nutrition log exists for the new day yet, both values show `0`

Weekly goal behavior:
- Home uses structured weekly goal snapshots when available
- if no snapshot exists for the current week, the app can create one lazily
- prior unfinalized snapshots are finalized lazily when the user enters a new
  week

Relevant files:
- `app/home/page.tsx`
- `src/lib/date/getIsraelDateKey.ts`
- `src/lib/weeklyGoalSnapshotService.ts`

5. WEEKLY GOAL SNAPSHOTS
================================================================================

Purpose:
- persist weekly goal history as structured data
- keep weekly focus stable through the week
- support future weekly history/monthly summary/week-over-week comparisons

Persistence model:
- table: `public.weekly_goal_snapshots`
- migration: `supabase/migrations/20260405_create_weekly_goal_snapshots.sql`

Snapshot structure includes:
- `user_id`
- `week_start_date`
- `week_end_date`
- `goal_type`
- `template_id`
- `title`
- `body`
- `focus_area`
- `primary_metric`
- `targets` jsonb
- `actuals` jsonb
- `outcomes` jsonb
- `confidence`
- `created_at`
- `updated_at`
- `finalized_at`

Integrity:
- unique per user/week by `unique(user_id, week_start_date)`

Flow implemented:
- create current-week snapshot if missing
- get current-week snapshot
- finalize previous snapshots lazily when a new week has started

Weekly calendar rule:
- week starts Sunday 00:00
- week ends Saturday 23:59:59
- snapshot identification uses that Israeli week model

Decision stability:
- weekly display window and decision window are separated
- weekly recommendation selection uses broader signals
- weekly snapshot persists the selected weekly focus so it does not jump around
  mid-week

Relevant files:
- `src/lib/weeklyGoalSnapshots.ts`
- `src/lib/weeklyGoalSnapshotService.ts`
- `src/lib/repositories/weeklyGoalSnapshotRepository.ts`

================================================================================

Route:
- `app/workout/page.tsx`

Workout page responsibilities:
- load active program day
- restore in-progress workout draft
- run live timer
- log sets with weight/reps/difficulty
- save session into workout session tables

Draft persistence:
- `src/lib/workoutDraftStorage.ts`
- workout state is persisted locally during an active workout
- timer restoration uses real elapsed time from stored `startedAt`

Current workout session save model:
- `workout_sessions`
- `workout_session_exercises`
- `workout_session_sets`

Recent live-workout improvements:

1. Persistent timer across app exit/reopen
- if the app closes during a workout, reopening restores the draft
- timer is recomputed from the stored start time
- timer continues until the user resets or saves

2. Add extra exercise during active workout
- visible only during active session
- button label: `הוסף תרגיל`
- minimal modal form:
  - exercise name required
  - planned sets optional
  - planned reps optional
  - planned weight optional
- numeric values must be non-negative

Extra exercise state model:
- appended into the same `draftExercises` array as regular exercises
- represented like a normal draft exercise with:
  - `exerciseId: ''`
  - `exerciseName`
  - planned values
  - `completed: false`
  - `durationSeconds: 0`
  - `sets: []`

Post-insert behavior:
- can receive sets normally
- uses the same set editing/difficulty flow
- persists in workout draft storage
- is included in normal workout save payload

Why it appears in history:
- it is saved through the same session tables as regular exercises
- history pages already render saved session exercises generically
- no special-case history UI is required

Relevant files:
- `app/workout/page.tsx`
- `src/lib/workoutDraftStorage.ts`
- `src/lib/repositories/workoutSessionRepository.ts`

Recent workout edit improvements:

1. Editable session time boundaries
- workout edit flow supports editable start time and end time
- duration is derived from those times instead of being entered manually

2. Per-exercise duration editing
- each saved exercise duration can be edited in workout edit flow

3. Duration consistency fixes
- duration calculations are normalized to reduce mismatch between session-level
  and exercise-level time values

11. ARCHITECTURAL PATTERNS
================================================================================

1. Repository pattern
- page components do not call Supabase directly
- data access goes through repository/service modules

2. Deterministic business logic
- recommendations are selected from fixed templates
- weekly snapshots store structured fields, not generated prose

3. Local draft persistence for active workout
- active workout state is persisted locally
- app can recover in-progress sessions and timer state

4. Timezone-safe daily logic
- Home "today" logic uses Israel-time helpers, not naive UTC slicing

5. Lazy finalization instead of background jobs
- weekly snapshot finalization happens when the user enters the app in a new
  week
- no cron/background scheduler is required

6. RTL-first product
- Hebrew UI
- RTL layout
- mobile-first screens

14. 2026-04-13 - SAME WORKOUT DAY AUTOFILL INVESTIGATION
================================================================================

Files inspected:
- `app/workout/page.tsx`
- `app/workout-history/page.tsx`
- `app/workout-history/[id]/edit/page.tsx`
- `src/lib/repositories/workoutSessionRepository.ts`
- `src/lib/repositories/programRepository.ts`
- `src/lib/workoutDraftStorage.ts`

Findings:
- current workout-day identity comes from `WorkoutProgramDay.id`
- the active workout screen stores that value in `selectedDayId`
- workout drafts persist `selectedDayId`
- saved workout sessions normalize day identity as `dayId = workout_program_day_id || day_id || ''`
- saved sessions also keep `dayName`
- save flow sends `p_day_id`, `p_day_name`, and `p_program_id`
- exercise identity comes from program exercise row `id` and is saved/read as `exerciseId`

Minimal matching rule:
- same workout day should match by saved `dayId` against current `selectedDayId`
- if a history row has no `dayId` (legacy compatibility path), fallback to `dayName`
- exercises should match by `exerciseId` first, then fallback to normalized `exerciseName`

Conclusion:
- no DB migration is required for a minimal solution using existing workout history data
- a migration would only be needed if we wanted to backfill older legacy rows that were saved without day/exercise ids
- for the current feature, use id-first matching with name fallback only for legacy rows

16. 2026-04-25 - USER FITNESS DATA EXPORT
================================================================================

Goal:
- give the user a one-click download of all their data as a Markdown file
- file is intended to be handed to an external AI fitness coach
- export must contain only data owned by the current authenticated user

Behavior:
- new button on `/profile` page labeled `ייצוא כל הנתונים`
- clicking the button:
  1. fetches the bundle through repositories (no Supabase calls inside the page)
  2. resolves effective nutrition targets via `resolveEffectiveNutritionTargets`
  3. renders structured Markdown via a pure utility
  4. triggers a browser download of `fitness-export-YYYY-MM-DD.md`
     where the date key uses Asia/Jerusalem (`getIsraelDateKey`)
- shows loading state (`מייצא...`) and disables the button during export
- shows a success message with the file name on completion
- shows an error message in red on failure
- Hebrew RTL UI is preserved; the Markdown content itself uses English section
  headers for AI-agent friendliness

Markdown sections:
- Header: generatedAt, timezone, exportVersion, userEmail
- Profile (table): full name, email, auth provider, age, gender, height, goal,
  experience, focus areas, training days per week, profile created/updated at
- Nutrition Targets: mode, daily calories target, daily protein target, plus
  raw manual override values from the profile row when present
- Bodyweight Log (table): date + weight (kg)
- Body Measurements (table): per-date chest, waist, abdomen, hips, arms,
  thighs, neck (cm), and notes
- Nutrition Logs: per-date heading with totals + raw input + per-item lines
  including kcal/protein/carbs/fat and reason if any
- Workout Sessions: per-session heading with date + day name, started/ended,
  duration, energy level, reorder count, and per-exercise details (planned vs
  completed, exercise duration, ordered sets with weight/reps/difficulty)
- Weekly Goal Snapshots: per-week heading with goal type, title, body, focus
  area, primary metric, confidence, targets/actuals/outcomes (JSON), finalized

Empty sections:
- each section gracefully shows "_No records found._" instead of an empty table

Files added:
- `src/lib/repositories/userExportRepository.ts`
  - `fetchUserExportBundle()` aggregates current-user data using existing
    repositories where possible (bodyweight, body measurements, nutrition logs,
    workout sessions, weekly goal snapshots) plus a focused profile read
- `src/lib/export/userFitnessExportMarkdown.ts`
  - `renderUserFitnessExportMarkdown(input)` pure function that produces the
    Markdown text from a typed input bundle
  - exports `USER_FITNESS_EXPORT_VERSION` (`1.0.0`) and
    `USER_FITNESS_EXPORT_TIMEZONE` (`Asia/Jerusalem`)
- `src/lib/export/userFitnessExportService.ts`
  - `buildUserFitnessExport()` orchestrates fetch + targets + render and
    returns `{ fileName, markdown, generatedAt }`
  - `downloadUserFitnessExport()` triggers a browser download via Blob URL

Files changed:
- `src/lib/repositories/weeklyGoalSnapshotRepository.ts`
  - added `listWeeklyGoalSnapshotsByUser(userId)` for the export flow
- `app/profile/page.tsx`
  - added export button, `handleExportAllData`, `isExporting`/error/message
    state, and import of `downloadUserFitnessExport`
- `PROJECT_SUMMARY.txt` updated (this section)

Architectural notes:
- no DB calls in the page component; all reads go through repository modules
- ownership is enforced by `user_id = auth.uid()` filters inside each
  repository (and Supabase RLS already constrains rows to the current user)
- Markdown generation is a pure function, easy to unit test

Limitations:
- the current schema does not store `birthdate` or `activity_level` on
  `profiles`, so the export uses the existing `age` field and notes that those
  two fields are not stored by the app
- workout timing in the export uses session-level `started_at`/`ended_at`/
  `duration_seconds` and per-exercise `duration_seconds`; if a session was
  saved before timing fields were introduced, those fields render as `-`
- nutrition log items inherit the existing `calculated`/`unresolved` status
  from `nutrition_log_items`; unresolved items are still included with their
  reason text so the AI coach has full context
- the workout program (`workout_programs` / `workout_program_days` /
  `workout_program_exercises`) is not duplicated in the export — the export
  focuses on logged history; users can re-export later if their program
  changes
- the export is generated client-side and downloaded directly; no server
  endpoint, no temporary storage in Supabase Storage

19. 2026-05-04 - WORKOUT DAY IDENTITY FIX FOR ABCD HISTORY/SAVE FLOW
================================================================================

Goal:
- fix a bug where an ABCD training week could save or display only day A while
  B/C/D sessions were missing or collapsed into the wrong workout day

Root cause:
- `/workout` tracked the selected workout day by `day.id` only
- when a program day had no stable `id`, selection could fall back to the first
  program day, causing saves for B/C/D to use A's day identity
- follow-up repository operations (`updateExerciseDurations`,
  `updateReorderCount`, `deleteWorkoutSession`) matched rows too narrowly by
  `day_id`, which was not sufficient for mixed legacy/current records

Implemented:
- `app/workout/page.tsx`
  - added a stable workout-day selection key: `day.id` first, otherwise
    `day.name`
  - updated initial selection, active-day lookup, and day button active state
    to use that stable key
  - kept previous-session prefill lookup using the real `day.id` plus `day.name`
  - save/overwrite follow-up calls now pass both `dayId` and `dayName`
- `src/lib/repositories/workoutSessionRepository.ts`
  - `updateExerciseDurations`, `updateReorderCount`, and
    `deleteWorkoutSession` now match the target session by:
    - `day_id`
    - or `workout_program_day_id`
    - or `day_name` for legacy/name-only rows
  - added minimal PostgREST filter escaping for those combined `.or(...)`
    clauses

Scope:
- no UI change
- no schema change
- no workout-history page rendering change
- fix is limited to workout day identity and repository row matching
